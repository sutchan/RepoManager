# Repo Manager 生产就绪规范 (Production Readiness) v2.3.10

> **定位**：定义产品达到「可投入生产环境」所需的质量门槛与验收口径，是八类非功能要求的**单一来源**。
> **权威关系**：本文说「要达到什么程度」；[`CONTRIBUTING.md`](./CONTRIBUTING.md) 说「怎么开发与评审」；[`MAINTAINERS.md`](./MAINTAINERS.md) 说「怎么发布与维护」；[`OPENSPEC.md`](./OPENSPEC.md) 是功能行为契约。
> **适用范围**：Go 产品本体（`cmd/repo-manager` + `internal/`）、CLI、GUI、落地页与发布链路；已弃用的 Next.js 参考界面（`src/`）只适用遗留代码的 lint / type-check 要求。
> **状态标注**：「已具备」基于 2026-11-24 实查；「目标」中带 `[待实现]` 的条目**尚未落地**，不得写成既成事实。指标数值为**拟定目标、待实测确立基线**后方可转为强制门禁。

## 1. 代码质量标准与审查流程

### 1.1 已具备
- `gofmt -l ./cmd ./internal` 无输出；`go vet -tags nogui ./...` 无告警，二者为 CI 强制门禁（`CONTRIBUTING.md` §2）。
- 导出符号须中文 doc 注释；错误处理显式、禁止 `_ =` 吞错；路径统一 `path/filepath`（§4.6）。
- 代码文件单文件 ≤ 200 行，按职责拆分且不改导出契约（§3.2 规则 5）。
- PR 流程固定：Issue → 短期分支 → 全门禁 → PR（模板）→ §9.2 清单审查 → merge commit（不 squash）；CODEOWNERS 已配置。

### 1.2 现状不足
- 无复杂度 / 重复率 / lint 扩展工具（`golangci-lint` 等），门禁仅覆盖格式与 `go vet`。
- 无审查响应时限或「谁可批准」的细粒度规则；§9.2 清单未覆盖安全 / 测试 / 性能维度。
- 无质量度量报表（变更失败率、回滚率、缺陷逃逸率）。

### 1.3 目标与检查清单
- `[待实现]` 引入 `golangci-lint`（govet / staticcheck / ineffassign / misspell）并纳入 CI `check` job；新增规则须给 2 周过渡期再转强制。
- `[待实现]` 圈复杂度 > 15 或函数 > 80 行的新增函数须在 PR 中说明理由或拆分。
- `[待实现]` §9.2 清单按本文 8 个维度分组，PR 模板同步增加对应勾选项。
- `[待实现]` 每季度统计一次变更失败率 / 回滚率，记入 `reports/quality-metrics-*.md`（产物，不作规范）。

## 2. 测试策略（单元 / 集成 / 端到端）与覆盖率

### 2.1 已具备
- 当前 **14 个 `*_test.go`、42 个 `Test*` 函数**，覆盖 `buildinfo` / `config` / `engine` / `i18n` / `logs` / `platform` / `cmd/repo-manager` / `internal/ui` 八个包（`OPENSPEC.md` §9.3）；CI 以 `-tags nogui` 运行 `go test -count=1`（含 `-race`）。
- §4.6 要求业务函数可测：扫描 / 白名单 / 配置 / 文案等纯逻辑须有测试，平台差异用接口隔离。
- CLI 入口纯逻辑（`parseArgs` / `resolveRoot`）与 GUI 纯逻辑（日志缓冲 / 进度解析）已覆盖测试；完整 GUI 交互与跨平台发版前仍按 `CONTRIBUTING.md` §9.3 做**手动冒烟**（隔离临时目录）。

### 2.2 现状不足
- **无覆盖率采集与门槛**：未生成覆盖率报告，`go test -coverprofile` 未接入 CI。
- **无分层定义**：单元 / 集成 / 端到端的边界、目录约定、禁用真实仓库根验证等只在零散段落出现。
- 无 e2e 自动化；GUI 回归完全依赖人工，易漏三语 / 二次确认 / 路径边界。
- 无 flaky 测试处理规则，无「测试失败时的回归用例补充」要求。

### 2.3 目标与检查清单
- **分层定义**（立即生效）：
  - 单元：`internal/*` 包内纯逻辑，不访问真实文件系统写操作；表驱动、并行安全用 `t.Parallel()`。
  - 集成：`internal/platform` + `internal/engine` 用 `t.TempDir()` 构造假项目，验证扫描 / 白名单 / 二次确认前置条件；禁止使用真实 `REPO_ROOT`。
  - 端到端：CLI 用 `os/exec` 调 `go run ./cmd/repo-manager`，GUI 按 §9.3 手动冒烟；e2e 只在隔离临时目录执行。
- `[待实现]` CI 增加 `go test -tags nogui -coverprofile=reports/coverage.out ./...` 与 `go tool cover -func` 摘要；产物写 `reports/`（已忽略）。
- `[待实现]` 覆盖率门槛：包均值 ≥ 80%，`engine` / `platform` / `config` 三个高风险包 ≥ 85%；`cmd` / `ui` 暂不设阈值（手动冒烟覆盖）。数据型描述按当前实况同步 `OPENSPEC.md` §9.3。
- `[待实现]` 每次 P1 缺陷修复须附回归测试；flaky 测试先 `t.Skip` 并登记 `tasks.md`，禁止直接删除。

## 3. 安全与合规规范

### 3.1 已具备
- [`SECURITY.md`](../.github/SECURITY.md) 定义私密报告渠道、安全边界（不越界删除、二次确认、白名单、隔离验证）与不适用情形。
- `CONTRIBUTING.md` §11 安全红线：无密钥入库、输入校验、删除目标只来自枚举、危险操作二次确认。
- `EXTRA_CLEAN_DIRS` 有路径穿越防护（`IsSafeCleanDirName`，见 `OPENSPEC.md` §5.3）。
- 日志与 Issue 提交要求脱敏（移除真实路径 / 用户名 / 密钥，`TROUBLESHOOTING.md` §7）。

### 3.2 现状不足
- `.github/` **无** `dependabot.yml`、CodeQL、依赖漏洞扫描（`govulncheck` / `npm audit`）；依赖更新仅靠 `go list -m -u all` / `npm outdated` 手工检查。
- 无 SBOM / 依赖清单产物；无「高危漏洞响应时间」承诺（SECURITY.md 明确不承诺 SLA，属事实，但缺内部处理流程）。
- 无敏感信息分级：`config.ini` 含本机路径、日志含执行细节；「哪些字段必须脱敏、保存到哪一级」未量化。
- 无权限控制规范：程序安装到只读目录（如 Program Files）时 `config.ini` / 日志写入失败的降级行为只见于历史审计产物，未进规范。

### 3.3 目标与检查清单
- ✅ `SECURITY.md` 版本与描述已同步（v2.3.7 核实）：头版本 `v2.3.7`、支持版本表「最新 `2.3.x`」、产品描述未出现双语措辞；原「立即修」项已关闭。
- `[待实现]` 新增 `.github/dependabot.yml`（gomod / npm / github-actions 三类生态，每周检查）；新增 `govulncheck ./...` 与 `npm audit --omit=dev` 到 CI（高危即阻断）。
- `[待实现]` 发版时生成 SBOM（如 `syft` / `go version -m` 输出），归档到 `reports/`，不随 Release 上传。
- **敏感信息分级（立即生效）**：密钥 / Token / 凭据（禁止入库，禁止写日志）；本机路径 / 仓库名（可写本地 `config.ini` 与日志，公开提交前必须脱敏）；功能统计（仅计数，不含项目名称）。
- **权限控制（立即生效）**：删除目标必须来自 `platform.ListProjectDirs` 枚举 + `filepath` 拼接；`config.ini` / 日志写失败时只警告并在 UI 提示，不阻断功能；禁止提权执行。
- `[待实现]` 安全审计节奏：每季度一次依赖审计 + 每次发版前一次高危漏洞扫描，结果记入 `reports/`。

## 4. 性能与可用性指标

### 4.1 已具备
- CI 已有 `windows-smoke` 与 `gui-build` 平台验证；`-dry-run` 提供无副作用的预演路径。

### 4.2 现状不足

- 无性能回归门禁与基线数据；递归扫描深度 3 层的最坏情况未做容量说明。

## 5. 日志监控与告警机制

### 5.1 已具备
- `repo-manager.log` 追加写入可执行文件同目录，CLI / GUI 共用 `logs.FileLogger`，带时间戳；打开失败降级为仅下游输出（`OPENSPEC.md` §2.4 / §6.2）。
- 结果区 / CLI 输出展示每步执行结果；危险操作在 `-dry-run` 下输出预演清单。

### 5.2 现状不足
- 无日志级别（DEBUG / INFO / WARN / ERROR）、结构化字段或统一错误码；无法按级别过滤或聚合。
- 无日志轮转 / 大小上限，长时间使用可能无限增长。
- 无告警机制：本地工具无集中监控是合理的，但 **CI 失败、发布校验失败、安全扫描高危** 尚无主动通知渠道。
- 「日志含本机路径，提交前脱敏」只是提示，未落到日志格式层面（如路径字段标记）。

### 5.3 目标与检查清单
- `[待实现]` 日志加级别前缀与稳定错误码（如 `E-CONFIG-READ`、`E-DELETE-SCOPE`），在 `OPENSPEC.md` §6 维护错误码表。
- `[待实现]` 单文件超过 10 MB 时轮转保留最近 3 个文件（本地行为，需同步 §6.2 与 TROUBLESHOOTING §1）。
- `[待实现]` GitHub Actions 失败通知：至少启用仓库 Notifications；安全扫描 / 发布校验失败时由 `MAINTAINERS.md` §3 的值班人处理。
- `[待实现]` 崩溃 / panic 捕获：记录最小堆栈到日志并提示用户按 `SUPPORT.md` 脱敏提交；不采集用户路径与仓库名以外的信息。

## 6. 部署与回滚流程

### 6.1 已具备
- `release.yml` 四阶段：`version` → `build`（4 目标）→ `package`（`RepoManager-v<版本>-<os>-<arch>.zip|.tar.gz` + `SHA256SUMS.txt`）→ `release`（校验同 SHA 其它工作流全绿）。
- 归档命名、校验脚本、产物保留与手动 `workflow_dispatch` 打包见 `CONTRIBUTING.md` §8.4 与 `MAINTAINERS.md` §3。

### 6.2 现状不足
- **无回滚规范**：发布后发现问题时如何切回旧版本、是否保留 `config.ini`、如何通知用户均未定义。
- 无预发布 / 灰度渠道（个人维护项目可简化，但目前完全缺失）。
- 无存档保留策略与废弃版本下架规则；`SECURITY.md` 只写「仅支持最新版」，无执行细节。
- 升级兼容性未说明：配置格式自 v2.2.0 起为 4 键，跨大版本升级时的键迁移规则散见 CHANGELOG。

### 6.3 目标与检查清单
- **回滚步骤（立即生效）**：
  1. 确认影响范围，按 `SECURITY.md` 判断是否需私密处理；
  2. 从 GitHub Release 下载上一稳定版归档，用 `SHA256SUMS.txt` 校验；
  3. **保留**可执行文件同目录的 `config.ini` 与 `repo-manager.log`（格式未变时）；
  4. 解压覆盖二进制，运行 `repo-manager -h` 确认版本与 build；
  5. 按 §9.3 做最小冒烟；在 `CHANGELOG.MD` 记录回滚原因与版本。
- `[待实现]` Release 保留最近 3 个稳定版归档，更旧版本仅在 `SECURITY.md` 列为不支持；不主动删除历史 tag。
- `[待实现]` 预发布用 GitHub Release 的 prerelease 标记，不单独建渠道；升级跨大版本时在 CHANGELOG 顶部写配置迁移说明。
- `[待实现]` 回滚演练：每半年在隔离目录演练一次上述步骤，结果记入 `reports/`。

## 7. 版本管理与变更记录

### 7.1 已具备
- SemVer + `internal/buildinfo/version.go` 单一权威源；`CONTRIBUTING.md` §8.2 列出 12 类展示位；§8.1 要求任何改动至少 bump 一次 patch。
- `CHANGELOG.MD` 按版本倒序、分组（Added / Changed / Fixed / Docs / Security 等）记录，发布前校验 tag 与小节存在。
- 页脚统一 `vX.Y.Z · build yymmddhhmm`，构建期注入，禁止硬编码。

### 7.2 现状不足
- 无废弃 / 弃用策略（deprecation policy）：功能弃用、文件弃用（如 `lang.ini`、`src/`）的告知周期与移除节奏未定义。
- 无「安全版本支持矩阵」的自动同步机制：`SECURITY.md` 曾长期停在 `2.2.x`（见 §3.2）。
- CHANGELOG 与 `tasks-done.md` 存在内容重叠，需明确「CHANGELOG 记变更、tasks-done 记任务闭环」。

### 7.3 目标与检查清单
- `[待实现]` 新增废弃策略：弃用公告 → 至少两个 minor 版本保留兼容 → CHANGELOG 标注 → 移除；`src/` 与 `lang.ini` 按此执行。
- `[待实现]` bump 清单扩展：把 `SECURITY.md` 的支持版本表纳入 §8.2 校验，避免再次漂移。
- **职责边界（立即生效）**：CHANGELOG 记录「用户可感知的变更」，tasks-done 记录「任务闭环过程」，两者不互为副本。

## 8. 文档完整性要求

### 8.1 已具备
- 文档地图 / 按角色阅读路径（`docs/README.md` §1 / §2）、唯一来源、三处登记、任务单一来源、双门禁（`check:docs` / `check:root-clean`）。
- 规范适用范围与优先级矩阵（`CONTRIBUTING.md` §1.1）；记忆文档时效与可信度标注（§10.11）。
- 根文档大写 `README.MD` / `CHANGELOG.MD`、`docs/` 下小写 `.md`；标题层级与术语表统一。

### 8.2 现状不足
- 双门禁只校验链接与根目录，**不校验内容事实**（三语、命令、版本号曾多次漂移）。
- 无文档 owner / 审阅周期；新增文档的三处登记靠人工执行。
- 无术语一致性自动检查（产品名 / 模块名 / 功能 1–7 / 语言代码）。

### 8.3 目标与检查清单
- `[待实现]` 事实一致性门禁：校验文档标题版本 == 权威源、CLI 命令与 `ci.yml` 一致、远程 URL 唯一、三语代码齐全，纳入 CI。
- `[待实现]` 每份 `docs/*.md` 在标题下加「所有者 / 最后复核日期」一行；每半年复核一次。
- `[待实现]` 术语表（`CONTRIBUTING.md` §5）作为唯一来源，新增术语先入表再写文档；`check:docs` 增加术语拼写检查。
- **立即生效**：规划项必须显式标注 `[待实现]` 或登记 `docs/tasks.md`，禁止写成既成事实；历史产物（`reports/`）不作事实来源。

## 9. 发布前生产就绪总检查

发版前由维护者逐项确认（任一不满足则不得发布）：

- [ ] §1 门禁全绿；PR 经 §9.2 清单审查，无绕过的 merge commit
- [ ] §2 覆盖率报告已生成并达到门槛；P1 缺陷均有回归测试；§9.3 三平台冒烟全过
- [ ] §3 依赖漏洞扫描 0 高危；`SECURITY.md` 版本与三语描述当前；无密钥入库
- [ ] §4 性能指标已实测且未超阈值 20%；无不明的性能退化
- [ ] §5 日志级别 / 错误码 / 轮转已就绪；CI 失败通知已启用
- [ ] §6 归档 + SHA 校验通过；回滚步骤可执行；升级兼容说明已写
- [ ] §7 版本展示位 12/12 一致；CHANGELOG 新小节存在；废弃项已标注
- [ ] §8 双门禁绿 + 事实一致性门禁绿；三处登记完成；无规划写成既成事实

> 带 `[待实现]` 的项目在门口径转为强制前，发版检查以「已具备」项为基线，并在 Release 说明中列出未达标项（透明发布）。
